A complete example — what to upload, shown on a Verilog design (click to open)

A benchmark is a specification plus implementations of it. Here the specification is alu_k3_8t: an ALU for ternary numbers with 8 digits (0 to 38−1 = 6560, held in 13 bits) and six operations that wrap around modulo 38. To add your implementation of it, you upload two files:

  1. manifest.json says what it is: the specification (k_value 3 and bitwidth 8 give the name alu_k3_8t), your source files and their language, and who you are.
  2. The design does the computing: a module mvl_alu_3_8bit with inputs a, b, opcode and outputs result, zero, negative, carry. Our tests connect to these ports by name (interfaces for every language).
  3. Its testbench prints one line per test: Test 1: ADD A=0 B=0 -> R=0 Z=1 N=0 C=0. Every line is recomputed with the reference model; to run our own tests, the library swaps this testbench for its own.

      What the manifest needs
      • module_type, k_value, bitwidth, operations — define the spec; the name is derived (alu_k3_8t). A new k_value or bitwidth creates a new spec on approval. Any kind of design may be submitted (e.g. register, multiplier); only alu has a reference model so far, so other designs are published as not verified.
      • files[] — filename + language for every uploaded source file. Checked against the reference model: {{ language_labels.values()|join(', ') }}. Any other language (e.g. Chisel, Haskell) is accepted and published as not verified.
      • source — human-authored, llm-generated (then generator.model is required) or reference.
      • submitter — name, e-mail, affiliation; shown as provenance.
      • license — must be CC-BY-4.0: by submitting you agree to publish under this license.

      Test output must follow Test N: OP A=.. B=.. -> R=.. Z=.. N=.. C=.. so the golden-model comparison can read it. The manifest is validated in your browser before upload.

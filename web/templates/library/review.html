Review process

Every submission goes through the same seven steps. Steps 1–6 are automated and finish within minutes; step 7 is a decision by a maintainer. The rules below are the rules the pipeline implements — nothing else is checked, and nothing is waived. You can follow each step on the submission's status page, including the full logs.

Steps, pass criteria and rejection reasons

#StepWhat is checkedPasses whenRejected when (automatic)What you see
1Schema manifest.json against the published JSON Schema; declared files vs. uploaded files. All required fields present with the right types; every declared file uploaded and every uploaded file declared; file extension matches the language; license is CC-BY-4.0; generator.model given when source is llm-generated. Any violation. The browser pre-validates, so this normally never reaches the server. One line per problem, with the JSON path.
2Lint Static checks on each source file. ≤ 512 KB; UTF-8 text without control characters; contains a main() / __main__ block / module / entity; no system(), process spawning, file or network I/O, eval/exec. Any violation. File name and the matched construct.
3Simulation vs golden model Compile and run each file with gcc / CPython / Icarus Verilog / GHDL, then compare against the reference model in two ways: A — every test vector the program prints itself; B — the program's test section is replaced by a harness fed with golden vectors (all operand pairs when kn ≤ 256, otherwise 50 seeded random pairs plus edge cases). Compiles; the run exits normally; 100 % of vectors in A and B match the reference model — result and Z/N/C flags. Compile error; runtime error, crash or timeout; any single mismatching vector (LOGIC_ERROR); no parsable test output (NO_OUTPUT); the strategy-B harness cannot be built or run because the harness interface is not met. Compiler/simulator log; the mismatching vectors (operation, a, b, obtained, expected); the strength label (exhaustive / random(N, seed) / self-reported).
4Formal (optional) Reserved for equivalence checking of RTL against a reference. Not enabled yet — always skipped, never a reason for rejection. skipped
5LLM review Reserved for an advisory model-based code review. Not enabled yet — always skipped. When enabled it will only annotate; it cannot reject. skipped
6Dedup SHA-256 of each file against every published implementation. No identical file in the library. A byte-identical file is already published. Link to the existing entry.
7Maintainer approval Human review of what the machine cannot judge. Name and parameters match the format; description is accurate; source, generator model and authorship are plausible; the implementation is a genuine design (not a lookup table of the expected outputs, not a trivial wrapper); files are readable. Decision with a written reason (both outcomes require one). Typical reasons: misdeclared parameters, misleading provenance, output tables instead of arithmetic, duplicate spec under a different name. The reason, verbatim, on the status page and in the entry's review history once published.

Timeline

  • Steps 1–6 run immediately after upload; a typical submission takes 1–5 minutes, VHDL with large operand ranges up to 10 minutes.
  • Step 7: a maintainer decides within 14 days of the automated steps passing. There is no e-mail notification — bookmark the status page.

After a rejection

  • A rejection is not a ban. Fix the reported problem and submit again; every submission gets a new number and a fresh pipeline run.
  • If you think an automated verdict is wrong (for example a golden-model mismatch you can show to be an error in the reference), write to qialiu@uni-bremen.de with the submission link. Confirmed reference-model errors are fixed, versioned and announced on the format page.

What "verified" means on a published entry

A teal badge means step 3 passed with the strength shown in the entry's verification record — it is a statement about simulation against the reference model, not a formal proof. The record lists the tool versions, the reference-model version, the vector count, the seed and the SHA-256 of the file, so the run can be repeated.

The library also keeps implementations that failed step 3 when they were produced by the project's own LLM pipeline (grey badge, full failure report). They are published deliberately: which model gets which specification wrong is part of what the library documents. External submissions are never published with a failed verification.

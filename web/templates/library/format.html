Benchmark format v1.0

Every entry in the library is a specification (what is computed) with one or more implementations (how it is computed, in a given language). Both follow the conventions below so that entries can be compared, verified and cited uniformly. When you reference the format in a paper, state the version: MVL Benchmark Library format v1.0.

1. Naming

Specifications are identified by a stable name derived from their parameters:

  • alu_k3_8t — ALU, radix k = 3, 8 digits (trits)
  • regfile_k3_8t_r16 — register file with 16 registers
  • cpu_k3_8t_p5 — 5-stage processor

Each implementation file carries the name of its specification and the customary extension of its language, so the implementations of one specification never collide. When a specification has several implementations in the same language, the file name also carries their source and identifier.

2. Reference semantics

A specification fixes the radix k and the number of digits n. Operands and results are words of n digits, each digit in {0, …, k−1}, written as the integer a = Σ ai·ki (range 0 … kn−1). The arithmetic performed on those words belongs to one of two families, chosen by k:

Family M — modular: the ring Z/knZ (k = 2, 3, 5, 6, 7, …)

Radix-k integer arithmetic with carry propagation — the direct generalisation of an unsigned binary ALU. With M = kn:

ADD(a + b) mod MC = 1 iff a + b ≥ M
SUB(a − b) mod MC = 1 iff a < b (borrow)
MUL(a · b) mod MC = 0
NEG(−a) mod MC = 0
INC(a + 1) mod MC = 1 iff a = M − 1
DEC(a − 1) mod MC = 1 iff a = 0
Z, NZ = 1 iff result = 0; N = 1 iff result ≥ ⌊M/2⌋

Whether k is prime (3, 5, 7) or composite (6) makes no difference to this family; the label "GF(3)" used in earlier versions of this site was inaccurate for these entries and has been replaced by Z/3nZ.

Family F — Galois-field: the ring GF(q)[x]/(xn) (k = q a prime power: 4, 8, 9, 16, …)

Each digit is an element of the finite field GF(q); a word is the polynomial a0 + a1x + … + an−1xn−1. There is no carry between digits. GF(q) is constructed from GF(p)[x] modulo the conventional irreducible polynomial (GF(4): x²+x+1 · GF(8): x³+x+1 · GF(9): x²+1 · GF(16): x⁴+x+1; the same choices as the galois library and standard tables, e.g. Lidl & Niederreiter).

ADDai ⊕ bi digit-wise in GF(q)C = 0
SUBai ⊖ bi digit-wiseC = 0
MULpolynomial product a(x)·b(x), truncated to degree < n (i.e. mod xn)C = 0
NEGdigit-wise additive inverseC = 0
INC / DECa0 ⊕ 1 / a0 ⊖ 1 (digit 0 only, no carry)C = 0
Z, NZ = 1 iff result = 0; N = 0 always

This is the truncated polynomial ring, not the extension field GF(qn): multiplication is truncated, not reduced by a degree-n irreducible polynomial. Entries of this family are labelled GF(q)[x]/(xn) to make that explicit.

3. Reference model (golden model)

The two families above are implemented once, as a small program written directly from the definitions in §2 — the operation tables of GF(q) and the word-level operations of both families, and nothing else. It does not use any language model, any benchmark of this library or any hardware simulator, so it is independent of everything it checks, and it is the only oracle used in step 3 of the review process. It is versioned: a correction changes the version, and every verification record states the version it was produced with.

How it is validated
A reference model is only useful if something independent pins it down, so it is checked against four things that do not come from this project:
  • Ordinary integer arithmetic. Family M is compared with the language's own arbitrary-precision integers — exhaustively for small kn, otherwise over 20 000 seeded operand pairs.
  • An independent Galois-field library. The addition and multiplication tables of GF(q) are compared entry by entry with the galois package under the same irreducible polynomial.
  • The algebraic axioms themselves. Associativity, commutativity, distributivity, identities and inverses are verified directly, together with the relations that tie the operations together: SUB after ADD is the identity, NEG is SUB from zero, INC is ADD of one.
  • The binary special case. At k = 2 the model must reproduce an ordinary binary ALU, including the carry and borrow rules.
The suite runs on every change; a mismatch is a defect in the reference model, not in the benchmark under test, and is fixed with a new version.

4. Test output

Implementations print their self-test vectors one per line so that the comparison in step 3 can read them:

Test  1: ADD A=0 B=0 -> R=0 Z=1 N=0 C=0
Test  2: SUB A=6560 B=1 -> R=6559 Z=0 N=1 C=0

Accepted variants: result= instead of R=, lower-case keys, and a numeric OP= field (0 = ADD … 5 = DEC). Flags Z / N / C are optional but compared when present.

Harness interface (strategy B)

For the injected-vector run the reviewer replaces your test section with its own driver, so the computational part must expose this interface. Submissions whose harness cannot be built or does not run are rejected at step 3 (the strength label of every published entry states whether B ran).

C<struct> alu_exec(uint64_t a, uint64_t b, <op> op)returns a struct with a result field and flags z, n, c (flat, or nested in a member such as flags); the type name is free; main() is replaced
Pythonalu_exec(a, b, op) -> (result, flags)flags has attributes z/n/c (or zero/negative/carry); the if __name__ == "__main__" block is replaced
Verilogmodule mvl_alu_<k>_<n>bit(clk, rst, a, b, opcode[3:0], result, zero, negative, carry)the testbench module is replaced; the DUT must settle within two clock periods
VHDLentity mvl_alu_<k>_<n>bit with the same ports (std_logic / std_logic_vector)the testbench entity is replaced; the harness drives rst = '1' for two clock periods, then applies each vector for two periods; not applicable when kn > 231−1 (32-bit integer I/O)

5. Manifest

A submission bundles its files with a manifest that declares the specification, the files and their languages, the provenance and the license. It is validated against a published JSON Schema before anything else runs, and the Submit page offers a filled template to start from. The same manifest travels inside every download archive, listing the files with their checksums.

6. Verification record

Each published implementation stores: whether it compiles and runs; the golden-model result over the self-reported vectors (strategy A) and over the injected vectors (strategy B) with the strength label exhaustive(N) — all operand pairs, used when kn ≤ 256 — or random(N=50, seed=42); the toolchain versions; the reference-model version; the SHA-256 of the file; and the simulator log. These appear on the benchmark page and in spec.json. The review process page states exactly which outcomes pass.

7. Download archives

Per-benchmark, library-wide and selection archives contain <name>/spec.json, the implementation files, manifest.json (filters, spec IDs, SHA-256 per file, format version, timestamp), LICENSE.txt (CC BY 4.0) and CITATION.bib. When several implementations share a language, the file name carries the source and id, e.g. alu_k3_8t_deepseek_12.c.
